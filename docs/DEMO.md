# ThinkRoom · 从三份观点资料开始体验

[返回首页](../README.md) · [English homepage](../README_EN.md) · [设计脉络](DESIGN_ORIGINS.md)

**一个人人都能理解的场景：关注两位作者、保存自己的笔记，然后围绕新问题重新调用这些观点。**

> 这里的材料是**完全虚构的合成数据**，与真实客户、个人、博主、企业无关。下面是“怎么试”的指南，**不是真实模型的运行结果，更不代表模型一定能给出正确建议**。

## 1. 这次要问什么？

一家虚构的小店考虑在客服中试用 AI。你保存了三份内容：

| 资料 | 观点 |
| --- | --- |
| [虚构作者 A：从小处开始](../examples/demo-perspectives/01-small-pilot.txt) | 先处理最常见、风险低的问题，观察真实效果 |
| [虚构作者 B：先确认边界](../examples/demo-perspectives/02-data-risks.txt) | 客户隐私、回答错误和维护成本必须纳入评估 |
| [虚构店主笔记](../examples/demo-perspectives/03-own-notes.txt) | 高频问题已知，但真实订单含个人信息，不可直接用于外部模型 |

你真正关心的是：

> **该不该马上用 AI 做客服？两位作者的看法有哪些冲突？我应该先验证什么？**

这比简单地“总结三份资料”更能体现 ThinkRoom 的目标。

## 2. 导入资料

按[项目首页的本地启动步骤](../README.md#本地启动无需付费模型的-mock-模式)开启后端 Mock 模式和前端，然后访问 http://127.0.0.1:5173/chat。

在**问答**界面，上传上述三个 `.txt` 文件，观察上传与处理状态。在系统提供资料选择时，把后续问题限定到这三份材料。

> Mock 只验证界面、接口与入库链路，不代表真实模型能忠实重构这三个人的观点，也不保证每个输入都会在 Mock 下提取出完整的结构化知识。

## 3. 试试三种提问深度

**日常问答：**

> 请只根据我上传的三份资料，说出作者 A、作者 B 和我的笔记分别强调什么。每条观点都指出来源。没有证据的地方请直接说不知道。

**简报生成：**

> 围绕“这家小店是否应立即引入 AI 客服”，整理支持理由、反对理由、尚缺的信息和一个低风险的下一步。请分清资料原文与推论。

**委员会讨论：**

> 请从试点速度、隐私安全和维护成本三个角度比较方案的风险与收益。保留不同意见，不要为了达成共识而掩盖证据不足。

切换模式会影响耗时与调用成本。当前委员会使用**预设分析席位**，不保证每个席位恰好对应这里虚构的作者或上述指定角色；这几个问题是观察方向，**不是对实际席位配置、效果或生成内容的承诺**。

## 4. 观察哪些关键差异？

- **来源可追溯：** 回答有没有引用真实导入的那份资料？
- **观点与事实分离：** 作者意见是否被错误包装成已证实事实？
- **范围可控：** 限定资料后，有没有把无关的外部信息混入结论？
- **证据不足：** 对于不知道的成本、准确率和实施效果，系统有没有保留不确定性？
- **多视角：** 委员会是否展示实际差异，而不是简单重复同一段答案？
- **长期可用：** 资料能否再次召回？被确认的判断是否能保存并用于之后复盘？

## 5. 如果要测试真实模型

Mock 不代表真实语义质量。使用实际模型需要自行安全注入 `OPENROUTER_API_KEY`、停用 `--mock` 并承担调用费用。请仅上传有权使用、允许发送给提供商的资料。测试结果会因模型、配置、上下文和质量门禁不同而变化。

不要直接把虚构示例输出称为“真实客户案例”，不要把预计效果写成“模型表现已验证”。

## 6. 如何为 README 制作真实截图？

只有在实际运行的界面上，使用以上合成资料完成可重复的演示，才可采集并发布截图。必须检查浏览器书签、地址栏、窗口标题、文件路径、用户名、会话历史、凭据以及图片元信息。Mock 演示明确标注 Mock；真实模型调用需另外说明模型和限制。

旧的[虚构图书馆试点资料](../examples/demo-evidence.txt)仍保留为兼容性的合成测试素材，不再作为首页的项目定位案例。
